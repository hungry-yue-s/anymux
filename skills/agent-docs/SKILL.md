# Agent 文档分窗

Anymux 是用户看这个终端所用的网页面板。面板右侧有一个分窗，能渲染 Markdown（含表格、Mermaid、KaTeX、勾选框）和自包含 HTML，文件一变就自动刷新。把长内容写成文件放进分窗，用户不用在对话历史里来回翻。

## 命令

命令写在全局指令的"Anymux 文档分窗"一节里（形如 `node ".../bin/anymux.mjs"`，下面记作 `anymux`）；没有那一节时试 `anymux`。命令失败就跳过打开这一步，照常回答，不要为此反复重试。

| 命令 | 作用 |
|---|---|
| `anymux doc path <主题> [--html]` | 打印草稿路径：项目内 `.anymux/docs/<主题>.md`，并把 `.anymux/` 写进仓库自己的 `.git/info/exclude`；不在项目里时放到面板数据目录。只建目录，不建文件 |
| `anymux open --dock <路径>[#标题]` | 在用户正看着的这个窗口旁边打开；已经打开的不重复开，`#标题` 跳到该节 |
| `anymux open --background <路径>` | 只加标签、不切过去（进度、日志这类一直在变的文件） |
| `anymux open --dock <新路径> --replaces <草稿路径>` | 草稿放进项目后，把原标签换成新路径 |
| `anymux git show <提交号> [--repo <仓库路径>]` | 打开这笔提交的说明、文件列表与 diff；默认当前目录。隔离 worktree 的提交用该 worktree 的路径 |

用户不在看这个窗口时，面板会后台加入该窗口的分窗，返回后直接显示；自动打开和后台加入都有提示，并可从通知列表回看。新 Tab 有“新”标记。不会切走用户当前窗口或抢键盘焦点，这些由面板处理，你不用判断。

Git 提交预览也按同样方式归窗和提示。完成已授权的提交后，传入实际提交号打开自己的那笔提交；命令省略提交号时，服务端在收到请求时把 `HEAD` 固定为完整提交号。它只查看，不切分支、不修改文件或暂存区。预览失败照常报告，不重复提交。

## 什么时候写文档

写：
- 预计超过一屏（约 40 行），或有多级标题、表格、对比；
- 方案、设计、调研、评审结论、计划或检查清单、Mermaid 图；
- 接下来要围着它讨论好几轮的内容；
- 用户说"写成文档"。

不写：简短回答、单条命令、是或否、报错诊断的简短结论；代码改动本身（代码已在文件里，需要时 `anymux open --dock` 打开那个文件）；用户说"直接说"或"不要文档"。用户的明确说法总是优先。

对话里不重复全文：给一行路径（说明已在右侧打开）和三到五行要点，不看侧栏也能知道发生了什么。同一主题继续改同一个文件，不另建 v2；要用户看某处时用 `#标题` 打开。用户可能在文件里改字或勾选勾选框（会写回文件），改之前先重新读文件，保留用户的改动。

格式：默认 Markdown。需要交互或可视化时写自包含 HTML（不引用相对路径的本地资源）；要跟随面板配色时按 anymux-presentation skill 接入。

## 文档放在哪

按顺序取第一个适用的：

1. 用户这次明确说的路径。
2. 项目约定：AGENTS.md / CLAUDE.md 里点名的文档放置规则。通用规则（如"设计方案放 docs/"）不改变某个 skill 自己规定的位置，只有点名那个 skill 的规则才算。
3. 正在使用的 skill 规定的位置和流程。例如 superpowers：设计在 `docs/superpowers/specs/`，计划在 `docs/superpowers/plans/`，执行进度在 `.superpowers/sdd/…/progress.md`。照 skill 的流程写、照它的审阅步骤让用户确认，不要另建草稿，也不要为位置再问一次。面板会自己发现这些文件并打开，你仍可以 `anymux open --dock` 指定跳到哪节。
4. 都没有：`anymux doc path <主题>` 给的草稿位置。

已经被别的文档引用的文件（例如计划引用的设计）不要中途挪位置。

## 草稿放进项目

草稿稳定后，判断它是否属于项目。一次性的内容（调研过程、一次性的评审意见、调试记录）保持草稿。

能确定就直接做，然后告诉用户放在哪：
- 用户指定了路径；
- 项目约定明确规定了这一类，并标明直接放；
- 按约定往已有文档追加一小段（例如往已知问题列表加一条）。

以下情况先问：
- 新建文件，约定里没有这一类；
- 推断出不止一个候选位置，或需要新建目录；
- 会对外：README、公开文档站、CHANGELOG；
- 大段改写用户写的内容，或要改索引文件；
- 内容里有本机路径、主机名、内部地址、个人信息（草稿原本不进 git，放进项目会被提交）；
- 项目会自动提交并推送时，问的时候写明"确认后会随本次任务提交并推送"。

不要拿写文件时的权限审批代替这一步：有的模式下根本不弹审批，审批也看不出为什么放这里。

### 怎么问

在草稿开头的 front matter 写下建议，面板会在文档上方显示一条提示栏，用户点按钮就会把答复填进你的输入框：

```yaml
---
anymux:
  status: proposed          # draft | proposed | placed | kept
  target: docs/agent-docs-design.md
  reason: 同类设计文档都在 docs/*-design.md
  alternatives: [docs/design/agent-docs.md]
  also: CLAUDE.md 加一行链接
---
```

同时在对话里用普通文字问一次，列编号选项，然后结束这一轮等用户回答。不要用菜单式的提问工具，那样用户没法直接打字回答，面板的按钮也填不进去。例如：

```
设计已定稿（右侧"agent-docs-design"）。建议放进项目：
  1. docs/agent-docs-design.md：同类设计文档都在这里（推荐）
  2. docs/design/agent-docs.md
  3. 先保持草稿
同时会在 CLAUDE.md 加一行链接；确认后随本次任务提交并推送。
```

用户为一类新文档选了位置后，顺便问一句要不要把这条规则写进项目的文档放置约定，和本次确认一起问，不另外多问。

### 放进去时

1. 目标已有文件：读出来合并，不直接覆盖；需要合并时先问。
2. 按项目风格整理：去掉 `anymux:` 这段元数据，统一标题和语言，改正相对链接（目录变了），图片移到项目的资源目录。
3. 用自己的写文件工具写到目标路径，删除草稿，只留一份。
4. `anymux open --dock <新路径> --replaces <草稿路径>`。
5. 按约定更新索引（README、CLAUDE.md 的链接等），按项目规则提交。

用户选"先保持草稿"时把 `status` 改成 `kept`，之后不再为它提议。
